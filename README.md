```bash
git clone https://github.com/5hvn5vk3/hotpepper-groumet-search

```

cd backend

# 11. こだわったポイント

## 11-1. FE型定義の整理と詳細APIのレスポンスDTO化

### 背景

開発途中の段階では一覧と詳細で型・取得責務が混在し、`/api/gourmet` が検索と詳細取得を兼ねていました。

### 対応

- FE型を用途別に分離（`ShopListItem` / `ShopDetailSupplement`）。
- `GET /api/gourmet/detail` を追加し、詳細補足情報の取得をBEへ移管。
- 詳細APIは `toGourmetDetailResponse()` で必要な10項目のみ返却。

### 効果

- 画面ごとの型の意図が明確化し、保守性が向上。
- 詳細モーダルの実装を簡素化。
- 一覧APIと詳細APIの責務分離により、変更影響を局所化。

### 補足

外部APIモデルとドメインモデルの完全分離までは行わず、レスポンス専用型への分離だけ行いました。

## 11-2. 入力バリデーションの厳密化（BE）

### 背景

不正なクエリがそのまま外部APIに流れると、原因切り分けが難しくなり、400系/500系の責務も曖昧になります。

### 対応

- `lat/lng` の同時指定、`NaN/Inf` 含む数値検証、`range` の範囲検証を実装。
- `keyword/address` は trim、`start/count` はデフォルト値を付与。

### テスト

- バリデーション失敗ケースをテーブル駆動で検証（型不正・欠落・範囲外）。
- 正常系で trim 結果とデフォルト値反映まで確認。

### 効果

入力不備をハンドラーで早期に検知し、利用者へ一貫した400エラーを返せるようになった。

## 11-3. 外部API異常系に対する耐性（BE）

### 背景

外部API連携では、通信・タイムアウト・レスポンス破損などの失敗が実運用で発生します。

### 対応

- `SearchGourmet` で通信失敗、非200、JSONデコード失敗、ボディ読取失敗をエラー化。
- `start/count` はAPI制約に合わせてクランプ（境界値保護）。

### テスト

- `RoundTripper` モックでタイムアウト/通信失敗/非200/壊れたJSON/読取失敗を再現。
- クランプ値（最小・最大）がクエリに反映されることを検証。

### 効果

外部要因による障害時でも、失敗モードを想定した安定した挙動を維持できる。

## 11-4. エラーレスポンスの安全性と一貫性（BE）

### 背景

APIキーや外部APIの生メッセージを露出すると、セキュリティとUXの両面でリスクがあります。

### 対応

- ログ出力時に `key=` パラメータをマスク。
- HotPepperエラーコードをHTTPステータスとユーザー向け文言にマッピング。

### テスト

- ログに生APIキーが残らないことを検証。
- エラーコードごとのステータス/文言マッピングを検証。

### 効果

情報漏えいを防ぎつつ、フロントに返すエラー契約を安定化できた。

## 11-5. 堅牢かつ運用性を意識したレートリミットの導入（BE）

### 背景

パブリックなAPIエンドポイントへの過剰なアクセスは、システム全体の可用性低下や外部API連携での意図せぬ課金・制限引き起こしに繋がるリスクがあります。

### 対応

- 特定のIPからのアクセス集中による他エンドポイントへの影響を防ぐため、APIごとに独立したIPベースのレートリミットを実装。
- 本番でのプロキシ/NLB環境を想定し、`X-Forwarded-For`、`X-Real-IP` に対応したクライアントIPの正確な判定を導入。
- 制限到達時には HTTP 429 と合わせて `Retry-After` や `X-RateLimit-*` ヘッダを返し、クライアント側へ明確に状況を伝達。

### テスト

- モックサーバーを用いた統合テストで、正常なリクエスト、制限の到達、制限解除までの動作を検証。
- リバースプロキシ環境を想定した `X-Forwarded-For` ヘッダとクライアントIPの紐付けのテストを完備。

### 効果

過剰なアクセスに対しても安定してシステムを保護しつつ、制限情報をクライアントに伝えることでUXの低下を防ぎ、運用時のログ監視や対応方針を立てやすくしました。

## 11-6. テスト方針（横断）

- テーブル駆動テストで主要な入力パターンをカバー。
- モックで外部依存を切り離し、異常系を再現可能に。
- ステータス・JSON構造・メッセージまで確認してAPI契約を中心に検証。

### 補足

BEテストは現在、検索APIを中心に整備しています。`GetGourmetDetail` / `GetGenreMaster` の専用テストは未実装ですが、共通で使う `handleServiceError` は `errors_test.go` で検証済みのため、共通エラー処理（HTTP変換・ログマスク）は間接的に担保できています。

## 11-7. BE型命名の整理（リファクタリング）

型名と配置を整理し、`types` では `HotpepperGenre` / `ShopPhotos` / `GourmetSearchResult` / `GenreMasterResult` を公開型として利用しています。  
また、HotPepper固有エラーは `service.HotpepperAPIError` として `service` パッケージに配置し、JSONデコード専用型は `service` 内の非公開型に集約しています。

# 12. デザイン面でこだわったポイント

## 12-1. 全体と外部リンクボタンの色彩

- Google Mapへの外部リンクボタン以外は赤系の色と無彩色で統一しました。HOT PEPPER グルメのロゴが赤だからです。
- Google Mapの外部リンクボタンは、ホットペッパーへの外部リンクボタンと区別しやすいように、赤ではない色を選びました。
  緑色にした理由の一つは、Google Mapのアイコンで画像検索し、過去のアイコンも現在のアイコンも緑色が多いことに気づいたのがきっかけです。
  この緑は地図らしさを表現しているのではないかと思いました。

## 12-2. ジャンルのタブ

- 機能一覧で申し上げたようにジャンルをタブで表示しています。プルダウンよりも操作の手間が少ないのが良い点だと思っています。
- 交互に色の明るさを変えることで「反復」のイメージをユーザーに与え、モバイル表示したときに見えていないタブが存在することをユーザーに想像させることを狙っています。

# 13. 自己評価

以下に申し上げるような問題点・課題点があります。

## 13-1. FE: UIとUXに関する課題

- タブを切り替えるとページトップを表示してしまうというUX上の問題点があります。
- モバイル表示時に、タブの横スクロールの存在が必ず伝わるようにしたいのですが、その適切な方法が分かりません。
  例えば完全に見えているタブの右隣にあるタブが必ず部分的に見えるようにすることができれば解決するとは思うのですが、これは実装の仕方が分かりません。
- 詳細モーダルの閉じるボタンが少し見えにくく、赤い丸の地に白いバツのボタンにした方がよかったと思っています。
- Windows 11 環境で公開先にアクセスした際、現在地の取得に時間がかかることがありました。
  現状の実装では、Geolocation API を `enableHighAccuracy: true` で取得しており、`timeout` を明示していないため、環境によっては取得待ちが長くなる可能性があります。
  今後は timeout/maximumAge の設定と、位置情報更新待ちと検索実行の分離で改善したいです。
- ブラウザで一度位置情報の取得を拒否すると、その後再びアクセスしてもブラウザの設定をユーザーが変えない限り、位置情報の取得の許可を求めることが永遠にできなくなるという問題があります。

## 13-2. BE: 接続維持型攻撃（Slowloris）への耐性

`main.go` で `http.ListenAndServe` をタイムアウト設定なしで使用しているため、
HTTP サーバーの `ReadHeaderTimeout` / `ReadTimeout` / `WriteTimeout` / `IdleTimeout`
がいずれも無制限になっています。

これにより、HTTP ヘッダーをわざと断片的に送信し続ける Slowloris 攻撃に対してアプリケーション層での防御がない状態です。
実装している IP ベースのレートリミッターはリクエスト受信完了後に動作するため、接続占拠型の攻撃には効果がありません。

本番環境では Render のリバースプロキシが前段に入るため部分的に緩和される可能性は
ありますが、アプリ側での制御ではないため、
`http.Server` に明示的なタイムアウトを設定することが本来必要です。

## 13-3. BE: クライアントIP判定の前提と残課題

現状のレートリミットは、`X-Forwarded-For` / `X-Real-IP` / `RemoteAddr` を使ってクライアントIPを判定しています。
Render 環境では `X-Forwarded-For` に接続元IPが追記される挙動の報告があり、実運用上は一定の効果が期待できます。

一方で、`X-Forwarded-For` はプロキシ構成や前段サービスの仕様変更の影響を受けやすく、常に「末尾IP=実クライアントIP」とは限りません。
そのため、現時点の実装は「偽装IP対策が完全に完了した状態」ではなく、「前段プロキシの挙動を前提にした暫定的な防御」です。

## 13-4. 環境構築について

ローカル開発において Docker / Docker Compose を導入できませんでした。

導入できていれば以下のメリットがありました。

- `docker compose up` 1コマンドでバックエンド・フロントエンドを同時起動できた
- Go のバージョンを `Dockerfile` に固定し、環境差異をなくせた
- Render へのデプロイ時も `Dockerfile` をそのまま利用でき、本番との環境差異をなくせた

フロントエンドは S3 への静的ホスティングのため、Docker の対象はバックエンドのみです。
