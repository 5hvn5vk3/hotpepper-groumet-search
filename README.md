# 8. 開発環境構築手順

## 8-1. 前提条件

- Go 1.25.x 以上
- Node.js 25.x 以上 / npm 11.x 以上
- HotPepper Web Service の API キー（[こちら](https://webservice.recruit.co.jp/)から取得）

## 8-2. 手順

### 1. リポジトリのクローン

```bash
git clone https://github.com/5hvn5vk3/hotpepper-groumet-search
cd hotpepper-groumet-search
```

### 2. バックエンドの起動

```bash
cd backend
export HOTPEPPER_API_KEY=<your_api_key>
go run .
# → http://localhost:8080 で起動
```

### 3. フロントエンドの起動（別ターミナル）

```bash
cd frontend
npm install
npm run dev
# → http://localhost:3000 で起動
```

### 4. ブラウザでアクセス

http://localhost:3000 を開く

> フロントエンドの `/api/*` リクエストは Vite の設定により自動的に `localhost:8080` へプロキシされます。  
> フロントエンド側の環境変数設定は不要です。

# 10. こだわったポイント

## 10-1. FE型定義の整理と詳細APIのレスポンスDTO化

### 背景

一覧と詳細で型・取得責務が混在し、`/api/gourmet` が検索と詳細取得を兼ねていました。

### 対応

- FE型を用途別に分離（`ShopListItem` / `ShopDetailSupplement`）。
- `GET /api/gourmet/detail` を追加し、詳細補足情報の取得をBEへ移管。
- 詳細APIは `toShopDetailSupplement()` で必要な10項目のみ返却。

### 効果

- 画面ごとの型の意図が明確化し、保守性が向上。
- 詳細モーダルの実装を簡素化。
- 一覧APIと詳細APIの責務分離により、変更影響を局所化。

### 補足

外部APIモデルとドメインモデルの完全分離までは行わず、レスポンス専用型への分離だけ行いました。

## 10-2. 入力バリデーションの厳密化（BE）

### 背景

不正なクエリがそのまま外部APIに流れると、原因切り分けが難しくなり、400系/500系の責務も曖昧になります。

### 対応

- `lat/lng` の同時指定、`NaN/Inf` 含む数値検証、`range` の範囲検証を実装。
- `keyword/address` は trim、`start/count` はデフォルト値を付与。

### テスト

- バリデーション失敗ケースをテーブル駆動で検証（型不正・欠落・範囲外）。
- 正常系で trim 結果とデフォルト値反映まで確認。

### 効果

入力不備をハンドラーで早期に検知し、利用者へ一貫した400エラーを返せるようになった。

## 10-3. 外部API異常系に対する耐性（BE）

### 背景

外部API連携では、通信・タイムアウト・レスポンス破損などの失敗が実運用で発生します。

### 対応

- `SearchGourmet` で通信失敗、非200、JSONデコード失敗、ボディ読取失敗をエラー化。
- `start/count` はAPI制約に合わせてクランプ（境界値保護）。

### テスト

- `RoundTripper` モックでタイムアウト/通信失敗/非200/壊れたJSON/読取失敗を再現。
- クランプ値（最小・最大）がクエリに反映されることを検証。

### 効果

外部要因による障害時でも、失敗モードを想定した安定した挙動を維持できる。

## 10-4. エラーレスポンスの安全性と一貫性（BE）

### 背景

APIキーや外部APIの生メッセージを露出すると、セキュリティとUXの両面でリスクがあります。

### 対応

- ログ出力時に `key=` パラメータをマスク。
- HotPepperエラーコードをHTTPステータスとユーザー向け文言にマッピング。

### テスト

- ログに生APIキーが残らないことを検証。
- エラーコードごとのステータス/文言マッピングを検証。

### 効果

情報漏えいを防ぎつつ、フロントに返すエラー契約を安定化できた。

## 10-5. テスト方針（横断）

- テーブル駆動テストで入力パターンを網羅。
- モックで外部依存を切り離し、異常系を再現可能に。
- ステータス・JSON構造・メッセージまで確認してAPI契約を固定化。

### 補足

BEテストは現在、検索APIを中心に整備しています。`GetGourmetDetail` / `GetGenreMaster` の専用テストは未実装ですが、共通で使う `handleServiceError` は `errors_test.go` で検証済みのため、共通エラー処理（HTTP変換・ログマスク）は間接的に担保できています。

# 11. デザイン面でこだわったポイント

## 11-1. 全体と外部リンクボタンの色彩

- Google Mapへの外部リンクボタン以外は赤系の色と無彩色で統一しました。HOT PEPPER グルメのロゴが赤だからです。
- Google Mapの外部リンクボタンは、ホットペッパーへの外部リンクボタンと区別しやすいように、赤ではない色を選びました。
  緑色にした理由の一つは、Google Mapのアイコンで画像検索し、過去のアイコンも現在のアイコンも緑色が多いことに気づいたのがきっかけです。
  この緑は地図らしさを表現しているのではないかと思いました。

## 11-2. ジャンルのタブ

- 機能一覧で申し上げたようにジャンルをタブで表示しています。プルダウンよりも操作の手間が少ないのが良い点だと思っています。
- 交互に色の明るさを変えることで「反復」のイメージをユーザーに与え、モバイル表示したときに見えていないタブが存在することをユーザーに想像させることを狙っています。

# 12. 自己評価

以下に申し上げるような問題点・課題点があります。

## 12-1. バックエンドのセキュリティ上の問題点

現在のバックエンドにはレートリミットが実装されていません。
そのため、同一IPアドレスからの短時間での大量リクエスト（DoS攻撃など）に対してノーガードな状態です。

具体的には以下のリスクがあります。

- サーバーリソース（CPU・メモリ）の枯渇によるサービス停止
- ホットペッパーAPIキーの無制限な消費による有料APIレート超過
- `ALLOWED_ORIGIN` によるCORS制限は curl や Postman では回避可能であり、ブロック手段として機能しない

## 12-2. UIとUXに関する課題

- タブを切り替えるとページトップを表示してしまうというUX上の問題点があります。
- モバイル表示時に、タブの横スクロールの存在が必ず伝わるようにしたいのですが、その適切な方法が分かりません。
  例えば完全に見えているタブの右隣にあるタブが必ず部分的に見えるようにすることができれば解決するとは思うのですが、これは実装の仕方が分かりません。
- 詳細モーダルの閉じるボタンが少し見えにくく、赤い丸の地に白いバツのボタンにした方がよかったと思っています。

## 12-3. 環境構築について

ローカル開発において Docker / Docker Compose を導入できませんでした。

導入できていれば以下のメリットがありました。

- `docker compose up` 1コマンドでバックエンド・フロントエンドを同時起動できた
- Go のバージョンを `Dockerfile` に固定し、環境差異をなくせた
- Render へのデプロイ時も `Dockerfile` をそのまま利用でき、本番との環境差異をなくせた

フロントエンドは S3 への静的ホスティングのため、Docker の対象はバックエンドのみです。
